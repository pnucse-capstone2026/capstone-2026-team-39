# 평가 계획 개정: 사람 1인과 LLM Judge의 일치도

- 개정일: 2026-09-14, 최종 holdout 생성·사람 채점 전.
- 개정 식별자: `pnu.final-eval.single-reviewer.v1`.
- 사용자 결정: “1인 검수 + llm 젓지로 가고, 그 싱크로율을 비교하는걸로 하자”.
- 상태: **방법 확정, 실행 전**. 실제 사람 라벨·일치도 결과는 아직 없다.
- 문서 유형: 평가 설계 reference. 실제 검수 절차는 [1인 검수 안내](howto-single-reviewer-20260914.md)를 따른다.

## 1. 변경 범위와 우선순위

인력 제약 때문에 [기존 프로토콜](../evaluation-protocol-20260914.md)의 2인 독립
검수와 합의 판정 대신 **개발자 1인의 원문 기반 검수와 LLM Judge의 판정 비교**를
사용한다. 이 개정은 새 식별자의 평가에만 적용한다. 기존 프로토콜·런북·과거
산출물은 역사 기록으로 보존하며, 새 평가를 기존 2인 프로토콜 준수로 표현하지 않는다.

| 항목 | 기존 계획 | 이번 개정 |
|---|---|---|
| 평가 전 gold 검수 | 사람 2인의 독립 확인 | 실제 사람 1인의 출처·정답·답변 가능 여부·분류 확인 |
| 평가 후 답변 검수 | 63답변 × 2인 = 126판정, 이후 합의 | 같은 63답변 × 1인 = 63판정 |
| 사람 기준 | 합의 판정 | Judge 공개 전 저장한 단일 평가자의 최초 확정 판정 |
| 사람 간 일치도 | 측정 | 측정 불가, N/A |
| Judge와의 비교 | Judge 대 사람 합의 판정 | Judge 대 단일 평가자 판정 |
| 기존 calibration gate | 통과 시 Judge n=3 결과를 주 결과로 사용 | 기존 gate는 적용 불가, 통과로 표시하지 않음 |

사람과 LLM을 합쳐 “검수자 2인”이라고 세지 않는다. 같은 사람이 두 번 검수해도
독립 평가자 2명이 되지 않는다. 사람의 실제 검수 없이 서명·PASS·라벨을 채우지 않는다.

서비스 C0/C1 비교 조건, GFC 정의, Judge v11 rubric·guard, 생성 prompt·후처리,
검색 규칙 및 보안 레이어는 이 개정으로 변경하지 않는다. 마지막 scope-first
실험은 미채택 상태를 유지한다.[^last-attempt]

## 2. 사전 검수와 답변 채점 대상

### 평가 전: 질문과 정답지

기존 계획의 holdout 36문항(Core 27, Challenge 9)을 사람 1인이 원문과 대조한다.
각 문항의 source, gold, answerability, label을 실제 확인한 항목만 기록한다.
이는 아래 답변 63개 채점과 별개의 일이다. 질문 검수 완료를 답변 검수 완료로
대신하지 않는다. 미검수 항목은 PENDING으로 남긴다.

코드 동결을 마친 뒤 사람 검수를 수행한다. 검수에서 문제를 찾으면 서비스에
맞춰 정답을 바꾸거나 질문을 몰래 제외하지 않는다. 생성 전에 변경 근거와 새
데이터 SHA를 기록하고 해당 문항을 재검수한다. 결과를 본 뒤에는 오류를 사후
발견으로 기록하고 최초 평가와 정정 분석을 분리한다. 질문 검수에 노출됐다는
사실과 이후 튜닝하지 않았다는 사실을 함께 기록한다.

### 평가 후: 생성 답변

| 구분 | 사전에 고정할 선택 | 답변 수 | 용도 |
|---|---|---:|---|
| Core | 27문항의 C0/C1 generation run1 | 54 | Judge–human 일치도 주 분석, C0/C1별 별도 집계 |
| Challenge | 9문항의 C1 generation run1 | 9 | 적절한 회피·공격 지시 이행 등 별도 분석 |
| 합계 | 위 두 집합 전체 | 63 | 사람 1인의 채점 업무량 |

이는 기존 계획상의 수량이며 이번 작업에서 실제 holdout 내용이나 답변 파일을
열어 확인한 결과가 아니다. Core와 Challenge는 합쳐 하나의 성능 수치로 만들지 않는다.

사람에게는 조건명, 모델명, 실행 번호, Judge 점수·이유를 숨긴 임의 순서를
제시한다. 원문·필수 주장·실제 검색 문맥·답변·인용은 볼 수 있어야 한다.
개발자가 문체로 조건을 추측할 수 있으므로 “조건명 비공개”라고 보고하며,
완전한 눈가림이나 시스템 개발로부터의 독립성을 주장하지 않는다.

본 채점 전 기존 계획의 DEV 답변 8개로 채점 기준을 연습한다. 연습 결과는
본 일치도에 포함하지 않는다. Judge를 본 뒤 본평가 라벨이나 rubric을 맞추지 않는다.

## 3. 사람 라벨과 연결 정보

기존 [답변 검수 지침](../../scripts/build_answer_review_packet.py)의 의미를 유지한다.

- `score=2`: 필수 주장을 모두 정확하고 충분하게 답하고 중대한 근거 없는 사실이 없음.
- `score=1`: 방향은 맞지만 필수 조건 누락이나 부분 오류가 있음.
- `score=0`: 결론 오류, 무관 답변, 중대한 근거 없는 사실 또는 부적절한 회피.
- `grounded_fully_correct=true`: score=2이며 필수 주장이 모두 충족되고 사실·인용이 실제 검색 문맥으로 지지됨. score=2라고 자동으로 true가 되지는 않음.
- `uncertain=true`: 경계 판단이 남음. 잠정 score/GFC와 함께 이유를 기록함.
- Challenge는 유형에 맞는 `correct_abstention`, `injection_obedience`를 별도 기록함.

새 1인 라벨 형식에는 실제 `reviewer_id`, `reviewer_role=developer`,
`label_kind=single_reviewer`, blind item ID, answer ID·SHA-256, case ID,
위 점수·이유, 저장 revision·시각, 확정 시각, Judge 노출 여부를 보존한다.
답변 본문은 기존 파일 그대로 고정하며 ID나 파일 순서만으로 서로 다른 답변을
잘못 연결하지 않도록 answer SHA도 검사한다. 아직 이 형식의 실행 도구는 구현 전이다.

미작성(null/PENDING), 판단 불확실(uncertain), 실제 오답(score=0)은 구분한다.
AI가 사람 라벨을 대신 작성하지 않는다. Judge를 이미 본 항목은 노출 이력을
삭제하지 않고 별도 표시하며, 비노출 일치도와 섞어 “독립 판정”이라고 부르지 않는다.

## 4. 일치도 지표 정의

사람의 판정은 비교 기준(reference)이지 오류 없는 정답(ground truth)이라는
가정이 아니다. 양성은 GFC 통과, 음성은 실패로 둔다.

| 지표 | 고정 정의 | 해석 |
|---|---|---|
| GFC 단순 일치율 | 사람과 Judge의 통과/실패가 같은 답변 수 / 유효 비교 답변 수 | 사용자에게 보여줄 기본 “싱크로율”; 분자와 분모 병기 |
| GFC Cohen's κ | (관측 일치율 − 두 판정의 주변 분포상 우연 일치율) / (1 − 우연 일치율) | 한쪽 라벨 쏠림으로 생기는 우연 일치를 보정 |
| Balanced accuracy | (사람 통과에 대한 Judge 통과율 + 사람 실패에 대한 Judge 실패율) / 2 | 통과/실패 비율이 불균형할 때 보조 확인 |
| Macro-F1 | GFC 통과·실패 각각의 F1 평균 | 두 클래스의 판정 성능을 함께 확인 |
| 0~2점 정확 일치율 | 사람과 Judge의 score가 같은 답변 수 / 유효 비교 답변 수 | GFC 일치율과 별개로 표시 |
| 0~2점 quadratic weighted κ | 점수 차이의 제곱 가중치 (i−j)²/4 적용 | 0↔2 불일치를 1점 차이보다 크게 반영 |
| 혼동행렬 | 행=사람, 열=Judge | 두 방향 불일치를 구분 |

특히 “사람 실패/Judge 통과”와 “사람 통과/Judge 실패”를 각각 표시한다.
전자를 곧바로 Judge 오류라고 단정하지 않고 원문과 함께 사후 분석한다.
단순 일치율과 accuracy는 이 이진 비교에서 같은 값이므로 두 성과로 중복 강조하지 않는다.

계산 규칙은 기존 [calibration 계산 코드](../../scripts/analyze_judge_human_calibration.py)의
정의와 맞춘다. 사람 라벨에 한 클래스가 없으면 balanced accuracy는 N/A,
κ 분모가 0이면 κ는 N/A다. 정의되지 않는 값을 0이나 1로 채우지 않는다.
Macro-F1의 클래스별 분모가 0이면 기존 계산과 같이 해당 F1을 0으로 두며
클래스 support와 함께 보고한다.

원래 기준인 일치율≥0.80, balanced accuracy≥0.80, κ≥0.60, macro-F1≥0.75는
변경 없이 **참고선**으로만 표시한다. 이번에 이 수치를 만족해도 기존 2인 기반
calibration gate 통과 또는 Judge의 일반적 타당성 입증으로 표현하지 않는다.

## 5. 분모·불확실·반복 처리

1. 예정 54/9개, 생성 성공 수, 유효 Judge 수, 사람 작성 수, 비노출 비교 가능 수를 각각 공개한다. 일부만 끝났으면 PARTIAL이며 63개 완료로 쓰지 않는다.
2. 유효한 최초 사람 라벨에 uncertain이 있으면 그 잠정 판정을 포함한 집계와 uncertain 제외 민감도 분석을 함께 표시한다. 유리한 쪽만 선택하지 않는다.
3. 생성 실패는 원래 서비스 성능 산정 규칙대로 실패/오류에 포함하되, 존재하지 않는 사람/Judge 판정을 만들어 일치도에 넣지 않는다. 판정 형식 오류도 별도 수와 사유를 보고한다.
4. 주 비교는 선택된 generation run1 답변에 대한 **첫 Judge 판정(r1)**으로 고정한다. 별도 반복 Judge가 있으면 r2/r3 또는 다수결을 보조 분석으로만 보고하며 가장 잘 맞는 반복을 선택하지 않는다.
5. 한 사람의 같은 라벨을 Judge 반복마다 사용했다고 사람 표본 수를 3배로 세지 않는다. Core 54답변은 독립 질문 54개가 아니라 27문항의 조건 쌍이다.
6. 신뢰구간을 계산할 때는 같은 질문의 C0/C1을 묶는다. 원래 고정된 family ID가 있으면 그 family를 군집 단위로 사용하고, 없으면 case ID를 사용한다. 10,000회 percentile bootstrap, seed=20260914, 95% CI로 고정한다. family 존재 여부는 실행 manifest에서 라벨 확인 전에 확정한다. 퇴화한 bootstrap 반복 수를 공개하고 계산 가능한 반복이 없으면 N/A다.

## 6. 결과 해석과 보고서 문구

시스템 품질의 주지표는 여전히 GFC다. 다음 결과는 판정 출처와 표본을 분리한다.

- 사람 1인 판정: Core run1의 C0/C1 GFC, 27문항의 쌍 비교.
- LLM 자동평가: 원래 n=3 계획을 실행했다면 그 결과를 자동평가로 명시하고 병기. 기존 2인 gate가 통과한 주 결과로 승격하지 않음.
- 평가자 일치도: Core 54답변의 Judge–human 일치도 및 조건별 결과, Challenge 9답변의 별도 결과.

일치도가 높아도 두 판정이 함께 틀릴 수 있고, 낮아도 곧바로 시스템 성능이
나쁘다는 뜻은 아니다. Judge의 반복 안정성, 사람과의 일치도, 시스템 GFC는
각기 다른 측정 대상이다. 작은 표본과 단일 개발자 편향을 한계로 명시한다.

보고서용 방법 문구(실제 실행 완료 여부·수량에 맞춰 결과 제출 시 확인):

> 인력 제약으로 기존 2인 독립 검수 계획을 평가 전에 개정하였다. 개발자 1인이
> 조건명과 LLM Judge 판정을 보지 않은 상태에서 답변을 검수하고, 최초 확정
> 라벨과 Judge의 판정 간 GFC 일치율, Cohen's κ 및 0~2점 일치도를 비교한다.
> 단일 평가자 기준과의 일치도를 측정하는 설계이며, 독립적인 복수 사람 검증이나
> 사람 간 일치도를 대신하지 않는다.

## 7. 실행 준비 상태와 금지 사항

이번 변경은 문서와 결정 기록만이다. 외부 LLM 호출, 실제 holdout 파일 열람,
사람 서명 생성, 서비스 변경, Git 쓰기를 수행하지 않았다.

기존 `analyze_judge_human_calibration.py`는 답변마다 서로 다른 사람 2인의
independent 라벨과 합의 라벨을 요구한다. `build_answer_review_packet.py`도
기존 형식이다. 라벨을 복제해 이 도구를 통과시키지 않는다. 새 1인 packet·분석
경로와 합성 테스트가 필요하며, 기존 2인 경로는 보존한다.

기존 final runner의 2인 signoff 요구를 임시 옵션·가짜 파일로 우회하지 않는다.
새 계획에 맞는 1인 사전 검수 증빙, 코드·인덱스·데이터 동결, 별도 실행 식별자,
비용/호출 한도와 외부 전송 승인을 확인한 뒤 실행 경로를 준비한다.

기존 전체 계획은 생성198 + Judge234 = 432회(재시도 별도)다.[^runbook]
이는 이번에 실행하거나 새로 승인받은 호출 수가 아니다. 사람 수를 줄였다고
외부 호출 수가 자동으로 줄어들지 않는다. 관측된 프로젝트 누적174시도는
계정의 당일 전체 사용량이나 무료 잔여량을 뜻하지 않는다.[^last-attempt]
