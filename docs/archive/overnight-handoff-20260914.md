## 1. 이번에 확인한 정확한 원인

고정 v2 추출 형식의 `query_scope`는 빈 배열이 가능하고, `scope` 객체의 필수
속성도 비어 있다. 따라서 범위가 모두 누락돼도 JSON 형식 검사는 통과한다.
그 뒤 고정 typed verifier는 질문 범위가 없으면 `query_scope_required`로 보류한다.

실제 모델 출력 DEV 1건의 결과는 다음과 같다.

| 단계/관측 | 결과 |
|---|---|
| 원래 v2 실행 | `quote_ambiguous`로 중단, 여전히 실패 |
| 직전 부모 근거 결속 사후 재생 | 인용 위치 2개를 별도 계약에서 확정 |
| 원본 추출 내용 | 4단위, 주장 7개, 근거 7개 |
| 질문 범위 | 0개 |
| 명시적 주장 범위 / 근거 범위 | 각각 7/7 빈 객체 |
| 본문 범위 / 제목 범위 참조 | 각각 0개 |
| 고정 verifier 결과 | 7/7 `uncertain/query_scope_required`, matched 0 |
| 이번 별도 readiness 검사 | 보류, 범위 선언을 임의 작성하지 않음 |

이는 **원래 v2 실행이 범위 검사까지 성공했다는 뜻이 아니다.** 원래 실행은
인용 모호성에서 중단했고, 뒤쪽 문제는 별도 부모 결속 사후 재생으로 드러났다.[^raw][^dev]

이 문항의 질문에는 2026년 사업명이 있고, 모델에게 제공된 앞 두 근거의 제목에도
같은 연도와 사업명이 들어 있다. 따라서 해당 범위가 입력 자료에 전혀 없어서
발생한 누락이라고 볼 수는 없다. 다만 모델이 왜 비웠는지 내부 원인은 관측하지
못했다. 형식의 선택 속성과 복합 추출 부담이 원인 후보이며, 제공자 내부 원인까지
확정한 것은 아니다.

### 중요한 정정: 빈 claim.scope 자체는 결함이 아니다

고정 verifier는 `effective = query_scope + explicit_claim_scope`로 판단한다.
문장에 사업명을 반복하지 않아도 질문의 범위를 물려받을 수 있다.
따라서 모든 주장에 범위를 중복해서 쓰도록 강요하면 정상 답변까지 막는다.

아래는 **합성 입력 8가지 조합**을 묶은 결과다. 실제 모델의 정답률이 아니다.[^synthetic]

| 질문 범위 | 명시적 주장 범위 | 근거 범위 | 고정 verifier |
|---|---|---|---|
| 없음 | 없음/있음 | 없음/있음 | 보류 `query_scope_required` (4조합) |
| 있음 | 없음/있음 | 없음 | 부족 `no_complete_scope_relation_condition_match` (2조합) |
| 있음 | 없음/있음 | 있음 | 조건부 `matched` (2조합) |

**질문 범위와 근거의 범위 결속을 먼저 확보해야 한다.** 단순히 claim.scope의
빈 객체 개수를 줄이는 것이 개선 목표가 아니다. 실제 응답은 어떤 범위도 채우지
않은 원문 그대로 분석했으며, 합성 입력만 인위적으로 조합했다.

## 2. 새로 만든 것과 적용하지 않은 것

- `evidence/scope-audit-20260914-v1/scope_audit.py`: 고정 검증기를 다시 거친 뒤
  주장별 유효 범위, 질문에서 물려받은 차원, 근거에 없는/추가된/충돌하는 차원,
  기존 verifier 이유를 기록하는 오프라인 검사.
- `run_offline.py`: 고정 DEV 재생, 합성 조합 분석, 기존 답변·판정 80쌍 검증,
  관련 시험과 SHA 목록을 새 경로에 보존하는 실행기. live 모드·자동 재시도 없음.
- `test_scope_audit.py`: 새 시험 31개. 기존 시험들과 합쳐 관련 시험 128개 통과.

별도 **범위 선언 형식 제안**도 작성했다. 사업/회차/연도/학기/대상/트랙/방향의
7개 차원마다 `specified`, `not_specified`, `unresolved`를 명시하고,
`specified`는 원래 질문의 정확하고 유일한 인용으로 결속한다.
질문에 없는 차원까지 만들어 채우지 않는다. 미확정은 부재로 바꾸지 않는다.
추출 결과와 선언이 다르면 다음 의미검증 단계의 로컬 사전조건을 만족하지 않는다.

이것은 **오프라인 schema 제안**이지 신규 모델 응답이나 서비스 prompt 변경이 아니다.
실제 DEV용 선언 응답을 대신 작성하지 않았다. 제공자 호환성도 미검증이며,
실행용 provider body나 새로운 호출 승인은 준비하지 않았다.[^contract]

### 검사 통과가 증명하지 않는 것

- 128가지 질문 범위 부분집합 중 선언과 일치하는 1가지가 로컬 사전조건을
  만족하고, 127가지 불일치는 보류됐다. 이는 합성 계약 시험이지 99% 정확도가 아니다.
- 연도가 원문에 있는데도 선언·질문 추출·주장·근거 추출이 **함께 연도를 빼면**
  이 검사도 놓친다. 알려진 한계로 시험에 고정했다.
- 환수/지급처럼 의미 태그를 양쪽이 함께 잘못 붙이면 정확한 인용이 있어도
  조건부 일치가 가능하다. 원문 기반 의미검증과 사람 calibration이 여전히 필요하다.
- 범위가 아예 없는 질문은 현재 고정 계약에서 보류된다. 자동으로 사업명/연도를
  발명하거나 고정 계약을 느슨하게 만들지 않았다.

모든 산출물은 `eligible_for_service=false`, `semantic_verified=false`,
`candidate_gfc=null`, `original_run_reclassified=false`다.

## 5. 다음 단계: 반복 오류보다 추출 과제 분리를 먼저

이번에 가능한 로컬 작업은 완료했다. 추가 평가 프로세스를 돌려 놓거나 API가
자동으로 이어지게 하지 않았다. 다음 실측은 다음 순서로 작게 설계하는 편이 낫다.

1. 동결 서비스와 별개인 실험 버전에서, 질문의 범위 선언을 먼저 검증하는
   작은 추출 과제를 정의한다. 질문 원문만으로 선언하고 근거/기존 Judge가 이를
   정답처럼 가르치지 않도록 한다. 부재 선언의 의미 정확성은 여전히 별도 점검한다.
2. 근거 추출에서는 제목·본문 범위를 정확히 결속하고, 원래 질문의 선언과
   불일치하면 조용히 빈 객체를 내보내지 않고 미확정 사유를 기록하게 한다.
   정상적인 질문 범위 상속과 실제 범위 충돌을 구분해야 한다.
3. 원래 질문·초안·모든 근거를 보는 독립 의미검증을 마지막에 둔다. 추출기의
   태그/자신감/선언 이유/이전 Judge 점수를 의미검증 정답으로 넘기지 않는다.
4. 처음에는 합성 1건 또는 고정 DEV 소수로 schema/결속/추출 완성률을 확인한다.
   전량 생성·Judge 재실행으로 바로 확대하지 않는다. 제공자/전송 내용/시도 상한을
   새 manifest에서 고정하고, 첫 오류 중단·재시도 0·단일 키·기존 산출물 보존을 유지한다.
5. 구조 통과율과 실제 GFC를 분리해 보고한다. 서비스 채택·동결 해제·holdout
   실행은 별도 판단이며, 합성 통과만으로 채택하지 않는다.

새 선언을 실제 모델이 얼마나 정확히 출력하는지, 잘못된 부재 선언이 줄어드는지,
과도한 거부 없이 GFC가 좋아지는지는 **미측정**이다. 이 단계를 생략하고
성능이 개선됐다고 보고할 근거는 없다.
